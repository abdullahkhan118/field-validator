# Concurrency & Execution-Ordering Review

## Why this mostly doesn't apply here

`field-validator` has no coroutines, no threads, no shared mutable state, and no runtime execution ordering to speak of — `annotations` and `runtime` are inert data/annotation classes, `processor` runs synchronously inside a single KSP round, and `sample` is a straight-line `main()`. Most checks from this skill's Android/general-Kotlin form (Handler posting, EventBus ordering, `postValue`/`setValue` races, dispatcher-affinity leaks) have **no applicable target** in this repo. Do not manufacture findings against nonexistent async code.

## The one real ordering concern: KSP multi-round resolution

`ValidatorProcessor.process()` is called once per KSP round, and its correctness *does* depend on ordering — but it's ordering KSP itself controls, not something the processor should try to control:

- `resolver.getSymbolsWithAnnotation(...)` returns symbols across the round's currently-visible source set; some may not be `validate()`-safe yet (e.g. a `@Validated` class referencing a type generated by another processor still running). The processor already handles this correctly: `symbols.partition { it.validate() }` splits resolvable from not-yet-resolvable, and **only the unresolved ones are returned**, telling KSP to retry them next round.
- **Check when reviewing any change to `process()` or `generateValidator()`:** does the change still return the `invalid` list unconditionally, or could a code path (e.g. an early `return emptyList()` added for a new special case) silently drop symbols that needed a retry? That would make affected `@Validated` classes fail to generate a validator with no compile error — the codegen equivalent of a dropped race.
- **Check `Dependencies` correctness on any new `writeTo()` call:** `Dependencies(aggregating = false, containingFile)` ties regeneration to the *specific* source file. If a future change makes one generated file depend on symbols from *multiple* source files (e.g. cross-class validation), `aggregating` must become `true` for that file, or KSP won't regenerate it when the second file changes — a correctness bug that looks like ordering/staleness ("my change isn't picked up") rather than a crash.

```bash
grep -n "return invalid\|Dependencies(" processor/src/main/kotlin/io/github/abdullahkhan118/fieldvalidator/processor/ValidatorProcessor.kt
```

## If concurrency is ever introduced

If a future change adds coroutines, threads, or shared mutable state anywhere in this repo (e.g. a parallelized processor, a runtime cache, an async validation API), re-derive the full check list from a general Kotlin concurrency-review skill at that point — checks for launch-then-read races, non-thread-safe lazy singletons, unsynchronized shared `var`s, and sequencing-by-delay all become relevant the moment that code exists. Until then, this skill's job is mainly to confirm "still nothing here to review."
